# Writable OAuth state for ephemeral GitHub Actions runners

Research date: 2026-08-22. This report uses official vendor documentation only and does not provision any service or inspect any real credential.

## Decision summary

**Do not use GitHub Actions repository or environment secrets as Ripple's production OAuth record.** They encrypt secrets before upload and can scope availability, but their API is deliberately write-only for secret values, exposes no value version or conditional-write precondition, and snapshots repository/organization secrets when a workflow is queued. A runner could overwrite a secret using a separately privileged GitHub App or personal token, but it could neither compare the stored value/revision first nor prove that it did not replace a concurrent refresh. That violates D22's compare-and-swap requirement; adding a privileged GitHub credential would also create a second long-lived secret solely to mutate the first. [GitHub secret encryption](https://docs.github.com/en/actions/concepts/security/secrets) [GitHub Actions secrets REST API](https://docs.github.com/en/rest/actions/secrets) [When Actions reads secrets](https://docs.github.com/en/actions/reference/security/secrets#when-github-actions-reads-secrets)

The leading **Phase 0 proof candidate** is one AWS Secrets Manager secret per live account, reached from GitHub Actions through a separate, account-scoped OIDC role. Its staging-label API supplies a useful compare-current-version primitive, but it is not by itself a complete production state protocol:

1. Transactionally load the account's `ready` state, approved exact `VersionId`, and credential revision; then fetch that exact secret version. Never use `AWSCURRENT` to choose the credential payload.
2. After a successful OAuth refresh, call `PutSecretValue` with a new UUID `ClientRequestToken` and a unique, non-sensitive pending staging label. Supplying a staging label prevents `PutSecretValue` from moving `AWSCURRENT` itself.
3. Call `UpdateSecretVersionStage` for `AWSCURRENT`, setting `MoveToVersionId` to the candidate and `RemoveFromVersionId` to the approved old `VersionId` loaded in step 1. AWS documents that the operation fails if the label is no longer attached to that exact old version. Treat that failure as D22's stale-CAS result and never overwrite the winner.
4. Remove the candidate's temporary label after success, or after a failed promotion. A crash-safe cleanup scan must remove abandoned Ripple-owned pending labels because Secrets Manager never removes labeled versions.

`ClientRequestToken` alone is only retry idempotency, not CAS. The conditional guarantee comes from `UpdateSecretVersionStage(RemoveFromVersionId=expected_old_version)`. [AWS `PutSecretValue`](https://docs.aws.amazon.com/secretsmanager/latest/apireference/API_PutSecretValue.html) [AWS `UpdateSecretVersionStage`](https://docs.aws.amazon.com/secretsmanager/latest/apireference/API_UpdateSecretVersionStage.html) [AWS secret versions and labels](https://docs.aws.amazon.com/secretsmanager/latest/userguide/whats-in-a-secret.html)

AWS states that Secrets Manager is eventually consistent, so the store CAS is **necessary but not sufficient**. A later runner cannot treat `AWSCURRENT` as immediately authoritative after promotion. Ripple needs a strongly consistent transactional record containing the exact approved `VersionId`, and runners must load that version explicitly; a temporarily invisible exact version produces a retryable read failure, never fallback to an older label.

The refresh call itself also needs a durable D16-style state machine. Before contacting Robinhood, the lease holder records `refresh_started` transactionally. It records the promoted exact version only after both broker refresh and secret persistence succeed. If the runner or lease disappears between those facts, the state is `refresh_unknown`; lease expiry never authorizes another automatic use of the old rotating refresh token, and human bootstrap/recovery is required. A fencing token still protects later transactional writes, but neither a lease nor secret CAS can revoke an external request already in flight. This protocol remains to be designed and proven before AWS can be selected. [AWS consistency warning](https://docs.aws.amazon.com/secretsmanager/latest/userguide/troubleshoot.html#ARN_secretnamehyphen)

## Required boundary from Ripple

D22 requires each live account to own a distinct OAuth registration and credential record shared only by its one-time bootstrap and its headless runner. The whole record—SDK token and client-registration models, absolute expiry, MCP resource, issuer, and authorization-server metadata—must be encrypted and replaced as one version. Invariant 9 excludes the record from Git, `OrderPlan`s, logs, caches, and uploaded artifacts.

The deployment mapping should therefore be:

| Ripple identity | GitHub boundary | Cloud identity | Secret access |
| --- | --- | --- | --- |
| Account A runner | protected `live-account-a` environment | OIDC role A | only secret A; load, add version, conditionally move/remove stage |
| Account B runner | protected `live-account-b` environment | OIDC role B | only secret B; same operations |
| Human bootstrap | local interactive identity, outside hosted execution | separately authenticated bootstrap principal | write only the selected account's initial record |

GitHub's OIDC token is short-lived; granting `id-token: write` only permits requesting that token and does not itself grant cloud access. AWS recommends constraining the trust policy's `aud` and `sub` to the intended repository and branch or environment, then using an IAM permissions policy for the exact secret ARN. Ripple should grant only `secretsmanager:GetSecretValue`, `secretsmanager:PutSecretValue`, `secretsmanager:UpdateSecretVersionStage`, and the minimum describe operation the adapter proves it needs. A customer-managed KMS key is unnecessary initially; if one is selected later, the role also needs narrowly scoped KMS permissions. [GitHub OIDC permission](https://docs.github.com/en/actions/reference/security/oidc#workflow-permissions-for-the-requesting-the-oidc-token) [GitHub OIDC with AWS](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws) [AWS GitHub OIDC trust policy](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_create-for-idp_oidc.html#idp_oidc_Create_GitHub) [AWS identity policies for individual secrets](https://docs.aws.amazon.com/secretsmanager/latest/userguide/auth-and-access_iam-policies.html)

GitHub workflow `concurrency` may reduce duplicate runs, but it is a scheduler control rather than Ripple's correctness boundary. The transactional per-account lease remains authoritative across retries, alternative schedulers, and future runner platforms.

## Why GitHub Actions secrets fail D22

| Requirement | Repository/environment secret behavior | Result |
| --- | --- | --- |
| Encryption | Libsodium sealed-box encryption before upload; GitHub decrypts for injection into a workflow. | Satisfies basic encrypted storage. |
| Read current revision | GET returns name and timestamps without the encrypted or plaintext value. | Cannot implement D22 `load` or verify a refresh write. |
| Atomic CAS | Create/update is an unconditional `PUT`; the API documents no ETag, expected revision, or `If-Match`. | Concurrent ephemeral runs are last-writer-wins. |
| Version recovery | No value-version list or rollback pointer is exposed. | Cannot safely recover the prior refresh record. |
| Least privilege | Environment protections narrow which jobs receive a secret, but updating it requires a separately authorized GitHub App/user token with Secrets write permission. | Adds a privileged credential and still does not add CAS. |
| Fresh visibility | Repository/organization values are read when the workflow is queued; environment values when the job starts. | A same-run write is not a durable read-after-write protocol. |
| Audit | GitHub audit events record secret-management actions, but the secret API exposes no content version to correlate with Ripple's revision. | Useful administrative evidence, not a credential state journal. |

The absence of CAS is an inference from the complete official create/update request and response schemas: neither repository nor environment endpoints accept or return a revision precondition. [GitHub Actions secrets REST API](https://docs.github.com/en/rest/actions/secrets) GitHub's audit-event catalog confirms that secret updates are administrative events, not value-version records. [GitHub secret audit events](https://docs.github.com/en/organizations/keeping-your-organization-secure/managing-security-settings-for-your-organization/audit-log-events-for-your-organization) Environment approvals are still useful for separating the two runtime identities, but the OAuth payload belongs in the external store. [GitHub deployment environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)

## Required hands-on proofs before adoption

No cloud credential store is demonstrated yet. The Phase 0 proof must use synthetic records containing no Robinhood token, account identifier, or other live data until the failure paths pass.

1. **OIDC identity isolation:** from environment A, prove role A can access only synthetic secret A; prove A cannot access B, role B, KMS administration, IAM administration, or secret enumeration. Repeat symmetrically for B. Prove an untrusted branch, pull request, and workflow without the protected environment cannot assume either role.
2. **Whole-record round trip:** store a maximum-shape synthetic D22 record, load it in a fresh hosted runner, and byte-compare the canonical serialized record without printing it. Confirm no payload reaches workflow logs, step outputs, command arguments, cache, artifact, or diagnostic bundle.
3. **CAS and pointer race:** start two isolated processes from the same approved exact version. Both create candidates; exactly one conditional promotion and transactional pointer update may become authoritative, the loser must return stale-CAS, and the approved exact `VersionId` must remain current in transactional state. Verify cleanup removes temporary labels without logging either payload.
4. **Crash injection:** terminate after candidate creation, after promotion, and before temporary-label cleanup. A later run must either recover deterministically or fail closed, and a janitor must remove abandoned Ripple pending labels without touching AWS-managed labels.
5. **Visibility failure:** immediately load the transactionally approved exact version from another hosted runner and inject not-found/stale-label responses. The runner may retry the exact-version read within a bound, but it must never select a different label or contact Robinhood until that exact record is available.
6. **Refresh ambiguity at the broker boundary:** persist `refresh_started`, then stop the runner before response, after response, before secret write, and before pointer commit. Every ambiguous case must become `refresh_unknown`; lease expiry or another runner must never retry the old refresh token automatically. Prove fencing rejects every late transactional write from the old runner.
7. **Rejected refresh and stale write:** prove `invalid_grant`, network ambiguity, access denial, KMS failure, and stage mismatch all fail closed without initiating browser authorization, registering a client, invoking a broker tool, or replacing current state.
8. **Audit correlation:** retain sanitized run ID, assumed-role session identity, secret ARN, old/new version IDs, CAS outcome, and AWS request IDs in Ripple's operational audit; later correlate the request IDs to CloudTrail events. Treat version IDs as non-secret correlation metadata; never record secret payloads or Robinhood identifiers. Verify read, candidate creation, promotion, cleanup, denial, and stale-CAS events are attributable, and define the alert/fail-closed policy for an audit trail that stops delivering events.
9. **Cost and retention:** run the expected low-volume call pattern for a month estimate, alert on unexpected version growth, and ensure no sustained `PutSecretValue` rate approaches AWS's documented warning of more than one write per ten minutes or its version-retention quota.
10. **Bootstrap handoff:** prove the local interactive bootstrap can write the initial record to exactly one selected account secret through a separate least-privilege human identity, then remove all local transient files and verify that the headless role cannot initiate bootstrap.

Passing these proofs would establish the deployment credential boundary, not the trading boundary. Broker tool authorization, account binding, transactional execution state, deterministic risk checks, and reconciliation remain separate gates.
